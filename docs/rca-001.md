# RCA-001: Orders API returned HTTP 500s after an unreviewed config change

| | |
|---|---|
| **Date** | 2026-10-12 |
| **Duration** | 16:06 to 16:37 (about 31 minutes), with heavy impact from 16:20 to 16:37 |
| **Severity** | SEV-2: partial outage of the orders API (about 1 in 4 requests failed) |
| **Detected by** | Prometheus alert `ShopApiErrorBudgetFastBurn` (SLO fast-burn alert) |
| **Author** | Venkata Gopi Perumalla |

> This was a planned failure exercise on my own EKS project, run to test the monitoring, alerting and GitOps rollback end to end. Times are approximate (Europe/London), read from Argo CD, Grafana and Prometheus.

## Summary
A configuration change merged to `main` set `api.failureRate: "0.3"` in `helm/shop/values-eks.yaml`. Argo CD deployed it automatically, and about 25% of requests to the orders API (`GET/POST /orders`) started returning HTTP 500. The SLO fast-burn alert fired, the cause was traced to the change through Argo CD's history, and the commit was reverted in Git. Argo CD rolled the fix out, and the error ratio returned to 0%.

## Impact
- About **25% of `/orders` requests failed** (peak error ratio 25.7%, as shown by the alert value 0.257).
- Health checks (`/health`, `/ready`) kept passing, so **Kubernetes saw the pods as healthy** and did not replace them. Only users noticed.
- The SLO is 99.5% success over 30 days, an error budget of 0.5%. A 25% error rate burns that budget about **50 times faster** than allowed.

## How it was investigated
1. **Grafana (Shop API dashboard):** the "Requests per second by status" panel showed 5xx (yellow) starting just after 16:06, and the error-ratio panel climbed to about 25%. Latency and restarts were normal, so this wasn't a performance or crash problem.
2. **Loki:** the query `{namespace="shop", app="api"} |= " 500"` showed failures only on `/orders`, across all api pods, so a bad node or pod was ruled out.
3. **Argo CD (History and rollback):** the most recent deployment was commit `90d63c5`, synced at about 16:06, which matched the start of the errors. Its diff added `api.failureRate: "0.3"`.

## Root cause
A configuration value that makes the API fail 30% of `/orders` requests (`api.failureRate: "0.3"`) was committed directly to `main` with a vague commit message and no review. Because Argo CD deploys `main` automatically, the change reached production within about 4 minutes, with nothing to stop it.

Contributing factors:
- **No pull request or review** was required for changes to deployment values.
- **Readiness and liveness probes check `/health` and `/ready` only,** which kept passing, so Kubernetes had no reason to stop the rollout.
- **No progressive rollout:** all pods received the change at once.

## Fix
Reverted the bad commit in Git (`git revert 90d63c5`) and pushed to `main`. Argo CD detected the change and rolled the api Deployment back to the previous ReplicaSet. No `kubectl` commands were needed, and the rollback is recorded in Git history.

## What went well
- The **SLO alert fired** within about 6 minutes of meaningful traffic hitting the bug, and didn't fire on the earlier low-traffic noise.
- **Dashboards and logs pointed straight to the cause** within minutes.
- **Rollback was one Git command**; Argo CD did the rest, and the fix is auditable.

## What didn't go well
- The bad change went straight to `main` with **no review**.
- **Detection depended on traffic:** with no load between 16:06 and 16:20, the problem was invisible.
- The commit message ("tune api settings") **didn't describe the change**, which would slow an investigation in a real team.

## Prevention actions
| Action | Type |
|---|---|
| Protect `main`: require a pull request and one approval for changes under `helm/` | Process |
| Add CI validation of Helm values (for example, fail if `failureRate` is above 0 outside test environments) | Technical |
| Use Argo Rollouts canary deployments, so a change reaches a small share of traffic first and rolls back automatically on high error rates | Technical |
| Add a synthetic check (e.g. a blackbox exporter probing `/orders` every 30s), so errors are detected even with no user traffic | Technical |
| Adopt a commit message convention that describes what changed and why | Process |
